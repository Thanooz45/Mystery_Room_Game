CASEFILE / AI MYSTERY ROOM — START COMMANDS
===========================================

Prerequisites
-------------
- Node.js 20 or newer and npm
- Docker Desktop (to run MongoDB locally)
- A Gemini API key (case generation requires it)

One-time setup (macOS — Terminal)
---------------------------------
1. From the project folder:

   cp .env.example .env

2. Open .env and set GEMINI_API_KEY. Keep the local values for
   MONGODB_URI, CLIENT_ORIGIN, and COOKIE_SECURE.

   open -e .env

3. Install packages and start MongoDB:

   npm install
   docker compose -f compose.local.yaml up -d

Start the app (macOS)
---------------------
From the project folder, run:

   npm run dev

Open http://localhost:5173 in your browser. The Express API runs on
http://localhost:5000. Stop the app with Control+C. Stop local MongoDB with:

   docker compose -f compose.local.yaml down

Production Docker deployment
-----------------------------
Configure .env with:
- NODE_ENV=production
- MONGODB_URI pointing to a managed MongoDB deployment
- GEMINI_API_KEY
- CLIENT_ORIGIN set to the public HTTPS origin (for example,
  https://mystery.example.com)
- SESSION_SECRET set to a unique random secret of at least 32 characters
- COOKIE_SECURE=true

Place a TLS reverse proxy in front of the app. The container publishes port
5000 only on localhost; configure the proxy to forward to 127.0.0.1:5000.
Then build and start the app from the project folder:

   docker compose up -d --build

View startup output:

   docker compose logs -f app

Check health:

   curl http://127.0.0.1:5000/api/v1/health

Stop the deployment:

   docker compose down

Do not use the local MongoDB compose file as a production database. Do not
commit .env or put production secrets in source control.

Deploy to Vercel (frontend) and Render (API)
--------------------------------------------
1. Push the project to GitHub. Do not commit .env.
2. In Render, create a Blueprint from the repository and use render.yaml.
   Enter MONGODB_URI, GEMINI_API_KEY, and CLIENT_ORIGIN when prompted.
   SESSION_SECRET is generated by the Blueprint. Set CLIENT_ORIGIN to the
   planned Vercel HTTPS URL, for example https://your-project.vercel.app.
3. For MongoDB Atlas, allow the Render service's outbound IP ranges in the
   Atlas IP access list. Avoid 0.0.0.0/0 unless you accept database access
   attempts from any IP address.
4. After Render deploys, copy its HTTPS service origin, for example
   https://casefile-api.onrender.com.
5. Import the same repository into Vercel. Use the project root, Vite,
   build command npm run build, and output directory dist. Add the Vercel
   environment variable RENDER_API_ORIGIN with the Render origin only (no
   /api/v1 suffix) before deploying.
6. Deploy Vercel. Make sure the final Vercel URL exactly matches CLIENT_ORIGIN
   on Render. If it differs, update CLIENT_ORIGIN in Render and redeploy there.
7. Check https://your-project.vercel.app/api/v1/health and then register and
   create a case on the Vercel website.

Keep GEMINI_API_KEY, SESSION_SECRET, and MONGODB_URI only on Render. The Vercel
configuration proxies /api/v1 requests to Render and disables API response
caching for session-specific responses. Vercel preview URLs are separate
origins; the app currently supports one exact CLIENT_ORIGIN at a time.

Run frontend and backend directly (macOS or Windows)
---------------------------------------------------
After completing the local one-time setup above, open two terminals in the
project folder. Make sure MongoDB is running and .env is configured.

Terminal 1 — Backend (Express API):

   npm run dev:server

Terminal 2 — Frontend (Vite):

   npm run dev:client

Open the frontend at http://localhost:5173. The backend API runs at
http://localhost:5000. Alternatively, start both terminals with one command:

   npm run dev
